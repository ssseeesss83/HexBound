# 剧本 + AI DM：目标架构与数据契约

设计版本 D0.2，2026-10-24；以下字段、接口与模块均为待实施设计。保留单实例服务和 SQLite 的当前部署前提。

## 1. 权威状态与服务边界

服务端状态是世界与规则的唯一依据。玩家输入、模型输出和作者内容均先验证，再进入事务。模型调用不占用房间锁或数据库事务。

| 组件 | 职责 | 不能承担的职责 |
|---|---|---|
| 剧本包 | 大纲、关键节点、判断条件、NPC 目标、怪兽卡引用 | 在进行中的房间中随编辑器变化 |
| 场景 DM | 理解意图、判定是否需要检定、生成当前可知叙事 | 写入 HP、资源、骰点或读取其他队隐私来回应玩家 |
| 剧情规划器 | 读取必要的 DM 剧情秘密，提出有限子树 | 直接发布文本给玩家、覆写已确认事实 |
| 行动规划器 | 将两种入口变成同一种 ActionProposal | 接受客户端传入的任意消耗、伤害或 DC 为权威 |
| 规则引擎 | 资格、目标、时序、资源、掷骰和状态效果 | 接受自然语言作为可执行程序 |
| 场景投影器 | 按成员与场景输出快照、事件、角色信息和 AI 输入 | 把整张图发到浏览器后再隐藏 |
| 任务调度器 | 实时优先、背景预取、预算、取消和过期检测 | 在远程模型请求期间锁住玩家命令 |

玩家端仅提供一种玩法：`script_ai_dm`。作者端的 AI 辅助编写是编辑工具；旧 `mode`、`interaction_mode` 经过迁移映射后仅作历史数据，不继续提供能改变裁定权限的路径。

## 2. 剧本是可汇合的图，编辑器呈树状导航

`ScenarioBook` 增加 `schema_version`、`ruleset_id`、`outline`、`fact_definitions`、`milestones` 和 `ending_constraints`。来源包版本在开团时冻结。主线节点只需要重要节点和进入条件，不要求穷举玩家选择。

| 节点类型 | 需要保存的内容 | 发布条件 |
|---|---|---|
| `key` | 关键冲突、可达成条件、替代路径、失败后果 | 有明确推进条件及可达结局或待续写出口 |
| `scene` | 可见描述、对象、NPC、动作建议、怪兽引用 | 对象与规则引用有效 |
| `frontier` | 续写契约与可选 fallback 场景引用 | 可从入口到达，续写信息完整；不假作结局 |
| `ending` | 结局适用条件与文本、收束事实 | 不自动生成后继，不绕过结局条件 |

`key` 与 `scene` 均可交互。`frontier` 是待实现的出口，不能直接激活成空场景；续写失败时仍留在之前可玩的场景，允许讨论、观察、其他合法动作及重试。剧本如果提供 fallback，必须经过同一套依赖和规则校验。

边包含 `id / from / to / condition / outcome / visibility / priority`。条件使用受支持的声明式树：`all`、`any`、`not`、`fact_equals`、`has_item`、`event_occurred`、`milestone_state`，有类型、深度与大小限制；禁止表达式求值或上传代码。技能检定的成功事件可改变事实，再由事实驱动边；选择技能不等于已经成功。

事实定义区分：世界前提、可变化状态、玩家知识、DM 秘密。世界前提不能被随机生成推翻；可变化事实须由已结算事件改变。例如 NPC 可被角色杀死，后续主线必须处理其死亡，不能为保护剧本把 NPC 悄悄复活。里程碑允许 `achieved / failed / bypassed / pending`，失败和绕行均有后续因果。

树编辑器提供：主路径标记、节点类型、条件面板、怪兽卡选择、续写面板、校验定位、版本差异和预览。汇合节点显示“引用到…”，不复制底层记录。循环显示返回引用并阻止无限展开。首次加载只展开关键路径；AI 扩展草稿必须先校验再纳入作者版本。

旧剧本迁移：现有节点保持 ID 与路由，非结局转 `scene`，结局转 `ending`，原动作转兼容边；不能因升级重新掷先攻、发奖励或更换遭遇。

## 3. 运行图与续写契约

作者包不可变；`campaign.runtime_graph` 保存房间生成的节点和边、`graph_revision` 以及来源记录。每个场景实例引用图节点，场景内对象状态独立。两队先后进入同一地点时，读取同一世界实体的当前状态，不复制出两个互不相关的 NPC。

建议的末端契约：

```json
{
  "frontier_id": "harbor-side-street",
  "summary": "队伍离开海关，准备跟踪运货人",
  "confirmed_fact_ids": ["lens-at-warehouse"],
  "unresolved_threads": ["运货人替谁工作"],
  "npc_goal_ids": ["courier-avoid-arrest"],
  "allowed_monster_ids": ["harbor-guard"],
  "candidate_milestone_ids": ["learn-lens-route"],
  "constraints": ["不改变已发生的海关对话与资源结算"],
  "fallback_scene_id": "customs-yard"
}
```

文字为原创示例；实际事实、NPC、场景和怪兽 ID 必须存在于冻结包或已验证扩展图。角色已知事实由服务端单独投影，不因放入此契约而全部公开。

规划器只返回 `GraphPatch`：`job_id / base_graph_revision / scene_instance_id / frontier_id / read_set / new_nodes / new_edges / continuation / source_metadata`。`read_set` 标记依赖的事实与实体版本。生成不能写角色资源、骰子、奖励、当前回合，也不能删改已访问节点、冻结主线或已确认事件。允许建立新的替代达成路径，必须引用可用规则动作和事实。

提交顺序：

1. 校验结构、节点上限、唯一 ID、条件类型、依赖与规则集。
2. 校验所有新增节点可从接入点到达，每条支路通向合法结局、已存在节点或带完整契约的 frontier。
3. 校验世界前提和已确认事实；不能仅靠模型自称“一致”。
4. 在短事务内重查图版本、事实 read-set、场景状态、任务 lease 和受众权限代次。
5. 同事务写图补丁、来源、任务完成回执；唯一 `job_id` 防止重复落稿。

**生成完成不等于角色已移动。** 图补丁只提供可选后继。角色转场由有权限的行动显式提交；战斗结束、消耗、奖励、场景切换不能由补丁连带执行。

同一房间的两个有效补丁可能竞争图版本。首个提交成功，另一个重新验证其 read-set；首版保守丢弃并排队重试，不盲目合并或覆盖。

## 4. 前瞻生成与抢占

任务分为：P0 玩家裁定及必需续写，P1 当前场景叙述，P2 即将偏离的浅层分支，P3 远端补全。优先级为产品内部策略，不向玩家显示技术术语。P0 永远先于后台任务，P1 不阻挡已可执行的规则动作。

初始预算建议：每房间最多一个后台远程调用；单次 1–3 个可玩节点、最多两层、每叶保留 frontier；不自动递归展开下一批。任务去重键包含场景实例、末端、图版本和事实指纹。数值为待压测参数，正式上线前记录配置与测量结果。

触发因素由服务端判断：可用后继不足、接近 frontier、已提交意图可能离开既有分支。规划器可提供偏离分类，不能用分类本身推进状态。只输入草稿不会改变剧情或触发无限生成。

`generation_jobs` 持久化：任务 ID、优先级、状态、场景、受众 epoch、基础版本、read-set、续写输入、尝试次数、预算、lease、超时、输出和幂等回执。状态：`queued → running → validated → committed`；异常分为 `cancelled / stale / retryable_failed / terminal_failed`。

玩家操作到来时，调度器停止派发 P2/P3 并取消本进程中的后台 HTTP task。供应商可能继续计费，不能承诺服务端取消等于远程推理已停止；取消后的结果不得持有写入资格。旧请求仍未物理返回时，也不得占住 P0 的逻辑许可。若供应商有独立并发限制，需保留实时容量并在实测中验证。

进程重启时恢复过期 lease；限定重试与退避，避免永久 running 或错误无限重试。普通聊天不取消生成；相关场景的事实、动作或成员变动才使依赖失效。两队行动也不应因同一个房间版本彼此取消。

## 5. 两种行动入口，一条结算管线

能力表与自由描述均形成 `ActionIntent`，包括角色、场景、目标、入口来源、描述或能力 ID。18 项技能表达“想怎么尝试”，不代表客户端有权选择 DC 或强行掷骰。复杂意图拆为可审阅的多个行动，不一次执行隐藏的整段计划。

管线：意图 → DM 情境裁定 → 服务端计划 → 玩家确认（必要时）→ 再校验 → 原子结算 → 事件 → DM 叙述。

`ActionProposal` 绑定 actor、场景、遭遇、回合、反应窗口、规则包、相关实体版本与过期时间，保存完整规则计划与机械代价。客户端确认只提交 `proposal_id + command_id`，不能回传已编辑的伤害、资源和结果。

普通无风险互动可直接提交；涉及资源、攻击、离开当前场景等重要后果时，显示目标、动作类型、预计消耗与已知风险再确认。隐藏 DC、敌方秘密和未知后果不强制公开，完整机械凭据按可见范围展示。

AI 可在规则允许的情境裁量范围内选择是否检定、适用技能、难度和后果类别；这些值先固定在服务端计划，再掷骰。规则写明的 DC、豁免、施法时间、伤害、范围、材料和资源由资料及处理器决定，不能被模型自由重写。

统一能力注册表连接 `ruleset_id + content_id → handler + supported_conditions + tests + status`。建角、人物卡、目录、行动菜单和 AI 工具共享该表。`reference` 不能显示成可自动执行能力；开发版本未实现机制明确返回限制，正式完整规则版本须补齐所选范围，不能以此阻断替代完成。

## 6. 场景实例、小队与世界一致性

新增房间级 `groups`、`scene_instances`、`world_entities`、`memberships`。小队是成员集合，场景实例是运行中的地点与局势，两者不混成同一概念。多个小队可处于同一场景；同一小队分开后须显式形成不同场景成员关系。

每场景保存当前 node、对象状态引用、遭遇、回合、公开知识、局部事件流、DM 记忆和行动队列；共享 NPC、物品和全局剧情事实由版本化世界实体维护。两队争夺同一唯一物品时，事务检查实体版本，只有一个成功，另一队得到已变化的后果，不能重复授予。

场景内行动串行；不同场景可并行规划，短事务仍串行写库。角色只能处于一个主动行动上下文，跨场景目标需明确距离、通信或效果规则许可。合队校验地点、战斗和时间边界，不把两个正在进行的先攻列表直接拼接；必要时等当前遭遇结束，或由显式的新遭遇建立统一先攻。

探索以逻辑时间推进。战斗场景按轮计时；会影响另一队的全局事件在共同的时间检查点提交，必要时暂停快进一方。长休、时限任务与共享 NPC 不能因一队快进而悄然跳过另一队正在进行的战斗。具体时间同步规则需纳入分队集成测试。

## 7. 文字交流与服务端权限

聊天、故事事件和动作收据独立显示。聊天不调用行动工具，不自动交给 NPC，也不作为可信事实进入 DM 记忆。需请求 DM 回答时使用独立动作入口。

| 内容 | 可读取者 | 写入或执行者 |
|---|---|---|
| 大厅交流 | 当前大厅成员 | 当前大厅成员 |
| 小队商量 | 事件发生时的小队受众，且当前仍有该历史权限 | 当前小队成员 |
| 场景故事与规则事件 | 事件的可知受众且当前有读取权限 | 服务端 / 场景 DM 的验证输出 |
| 行动草稿与未确认提案 | 本人 | 本人；服务端验证 |
| 角色完整构筑 | 本人；明确授权的协作者 | 本人及规则引擎 |
| 对外可见角色状态 | 同场景知情者；其他人仅桌务名册 | 规则引擎 |
| 主线秘密与规划草稿 | 剧情规划器及具备内容权限的作者工具 | 校验后的作者流程 / 图补丁事务 |

每条事件保存 channel、scene instance、actor、event kind、固化的 audience、membership epoch、时间和内部序号。读取同时检查“当时可知”和“当前可读”，默认新入队者看不到过去的秘密。离队后停止读取该频道历史；曾看到的内容无法从人的记忆或已导出的文件中撤回，但应用会清除旧缓存。

同一个 `can_read_event / can_access_scene / can_target / can_submit_action` 用于 HTTP、WS、历史分页、导出、角色详情、行动菜单、提案和模型上下文。私有事件数量、全局序号空洞和目标错误细节也不得成为探测其他队内容的路径。分页用服务端签名的、绑定 viewer/channel/epoch 的游标，客户端不累计条目数量推算偏移。

房主的开始、暂停、调队等桌务权限，与读取剧情秘密分离。管理账号的运维权限不通过游戏快照下发秘密。AI 规划器读取 DM 秘密的服务端上下文与场景 DM 的可见上下文严格分开；原始规划文本不直接成为玩家叙述。

前端日志缓存 key 包含 room、viewer、channel、membership epoch；身份和范围变化时销毁旧 records、DOM、未读数、引用预览及旧场景控件。服务端过滤和前端清理必须同时验收。

本次不实现分队语音，不增加语音令牌、媒体服务器或相关配置任务。

## 8. 并发、版本与幂等

保留底层 `storage_revision` 保护数据库保存，新增：

| 版本 / 序号 | 变化来源 | 用途 |
|---|---|---|
| `action_revision`（按场景） | 影响该场景合法行动的状态变化 | 行动和提案一致性 |
| `entity_revision` | 共享角色、物品、NPC、事实变化 | 跨场景资源与世界冲突检测 |
| `graph_revision` | 已验证图补丁 | 拓扑提交 |
| `membership_epoch` | 调队、退队、权限变化 | 快照、历史、缓存和在途请求撤权 |
| `channel_seq` | 该可见频道的新消息 | 增量聊天和事件读取 |

聊天可改变 storage revision，但不改变 action revision。HTTP 收到旧 storage revision 时重新读取并在事务内合并消息，不覆盖新机械状态。DM 叙述绑定已确认 action event 和相关 read-set，不用整个房间版本相等判断是否可发布；重复叙述不得重复执行动作。

命令去重键仍为 room/member/command ID；成功回执和所有消耗同事务保存。规则拒绝不扣费；规则内失败按事先确定的代价结算。连点、HTTP 超时重试、WS 重连均不可重掷或重发奖励。

## 9. 严格战斗所需的文本战场

文本界面仍需显式机械事实：位置或距离、速度、视线、遮蔽、掩护、体型、区域与持续效果、武器触及及目标。AI 提议的地形变化先经规则和事实验证；不能因自由描写产生未登记的物体或优势。

规则引擎补齐动作 / 附赠动作 / 移动 / 每次攻击 / 反应的合法时序，回合开始与结束触发，机会攻击、施法限制、专注、抗性与免疫、临时生命、倒地与死亡、区域友伤与效果到期。反应窗口允许合法的非本人回合操作；“非本人回合一律拒绝”不符合该目标。

正式规则模式移除当前固定 30 尺速度、固定 15 尺接近、无机会攻击、范围忽略友伤等简化规则。历史存档保留旧 ruleset/profile，明确显示历史规则；新房间不能借旧接口混入房规。新增机制逐项附官方章节和规则示例测试。

规则全集、导入门禁及实现顺序见后续任务规划；没有全部机械覆盖证据时不能发布“完整严格 5e”结论。
