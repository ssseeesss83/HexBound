### 已复现的问题

1. 本机 `core.autocrlf=true`，25 个 JSON 与 MIT 许可的 SHA-256 均和 manifest 不同；将 CRLF 还原 LF 后匹配。需通过 `.gitattributes` 固定来源字节，不能重算 manifest 掩盖换行变化。本轮只记录，不修改原始资料。
2. 通过 compendium 查询的法术状态为 automated 18、assisted 13、reference 288，总计 319。特性查询为 automated 12、reference 395，总计 407。数字是当前 API 标记，受下面映射缺陷影响，不能作为已经核准的机械覆盖率。
3. `abilities.feature_automation` 与 `characters._features` 使用不同 ID 归一规则。`action-surge-1-use`、`bardic-inspiration-d6` 等可能在目录与人物卡上出现不同支持状态。要统一注册表并做 ID 关系审计。
4. 效果注册器含不在所选 SRD 法术目录中的 `hex`。这不等于玩家已经能施放，但需要“处理器必须归属于选定包或独立声明扩展包”的校验。
5. `characters.py` 已有单职业成长、法术准备、职业资源和休息；种族、背景和专长收益仍有缺口。不能把完整目录误作完整建角。
6. `free_actions.py` 和现有能力处理有固定速度、抽象距离、无机会攻击、范围目标简化等房规。要达到本轮严格规则目标，需补齐空间与时序模型；不能只改说明文字。
7. 社区上游曾遗漏生命领域的 guardian-of-faith；已有显式 overlay。说明数量与哈希通过也不能证明官方全集对照完成。

采纳：先冻结官方范围清单、收齐来源并签收，再结构化导入；文本、构筑、执行分别验收。未实现机制在开发版本明确拒绝，但正式全集版本的门禁不能因此放宽。

## 多人交互与权限

| 代码位置 | 问题 | 必须覆盖的修正 |
|---|---|---|
| `backend/app.py` 的 public | 所有人获得同一 scene、combat、最近事件和队伍数值 | 按 viewer / 场景 / 受众投影 |
| `/api/rooms/{room_id}/events` | 仅验证房间身份，返回全事件 | 历史、导出、分页与 WS 共用权限 |
| 人物卡详情接口 | 其他成员完整构筑可读取 | 本人或明确授权；同场景只输出可见摘要 |
| director.build_context、叙述输入 | 直接读取全房间最近事件 | DM 输入也按知识范围投影 |
| command 与 add_dm_response | chat 共用 room.version，会使动作冲突或 DM 叙述过期 | storage / action / channel 版本分离 |
| `frontend/app.js` | 同一输入框切换聊天、扮演与动作 | 交流区和行动区物理分开 |
| `frontend/live-log.js` | records 累积，范围变化后旧记录可能留存 | viewer/channel/epoch 缓存键与主动销毁 |
| 前端日志导出 | 按返回条数累加偏移 | 改用服务端绑定权限的分页游标 |

采纳：小队与场景实例分开建模；事件固化当时受众并检查当前权限；角色不因房主身份获得秘密；反应须允许在别人回合合法触发。语音原评审建议作为未来接口考虑，**按用户最新指示，分队语音已从本次实施与验收移出**。

主代理执行 `python -m pytest -q`，环境返回 `No module named pytest`。因此本轮未获得通过的产品回归测试结果，也不将文档规划描述为功能已验收。未在共享环境中额外安装依赖。

本轮验收对象是设计文档：需求追踪、任务依赖、验收条件、文档链接、Git 提交和远端推送。功能开发时须安装仓库声明的开发依赖，并在修复数据换行问题后重跑现有测试；先记录基线失败，再区分新引入的问题。

## 合并后的关键决策

- 基础架构先于分队剧情：场景实例、权限和版本是生成子树可正确工作的前提。
- 数据审计先于正式导入；现有快照作为收集候选和比对材料，保持原文。
- 图补丁、规则计划和文字叙事是三种不同对象，均有独立的验证与可见范围。
- 生成任务不能占用玩家行动锁；取消资格和取消远程计算分开验证。
- 完整设计交付与完整产品交付分开标记，后者以任务门禁为准。

## D0.2 → D1.0 复审修订

三个专业 subagent 在初版合并后再次只读复审。以下问题均已进入 D1.0 目标契约和后续任务；尚未编写产品实现。

| 复审发现 | 采纳的修订 | 后续验收 |
|---|---|---|
| 仅能添加节点不能新增 NPC 或线索，会限制即兴 | GraphPatch 增加受验证新实体和事实定义，房间命名空间，不授予机械资源 | A20、A22 |
| 检定后等待续写没有持久行动状态 | pending_transition 关联原步骤回执，失败可重试，不重掷、不自动转场 | A21、A23 |
| schema 无法证明自由文本全部因果正确 | 结构事实确定性校验 + 独立语义审查及试玩，分别说明保证边界 | A20、A22 |
| 场景相同不等于知识相同 | 公共回应使用受众知识交集，个人补充单独事件 | A33 |
| 同 NPC 可能被两队各自复制进战斗 | 唯一 active_encounter 及时间归属 | A34 |
| 撤权时在途响应和回执仍可能泄漏 | 返回前检查 epoch，不重放旧私有快照 | A35 |
| 含私密事件的频道序号仍泄漏 | 不下发内部序号，只用可见流与不透明游标 | A36 |
| 全集验收缺少章节到记录的证明 | 官方章节 → 原始资料 → 结构化记录覆盖矩阵，保留纯说明文本 | A03、A05 |
| 整段行动一次结算破坏规则时机 | 分步骤状态机，支持神圣惩击、护盾术和法术反制窗口 | A37 |
| 严格规则不能只在战斗期间生效 | 共享游戏时钟和持续效果生命周期，覆盖探索 / 转场 | A38 |
| 不许出现新对象会限制即兴环境 | DM 新对象先验证登记，再参与机械结算 | A20、A22 |

设计已包含当前需求和最新语音范围调整；产品完成以 [任务规划](roadmap.md) 与 [验收矩阵](acceptance.md) 为准。
