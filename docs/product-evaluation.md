# HexBound 内容平台与跑团体验评估

评估日期：2026-10-23。基于首版代码与文档的产品审查；不是用户访谈结果，也不代表已经通过视觉验收。本文区分本轮实施要求与成熟度后续门槛，具体完成状态应看测试记录。

## 1. 现状与迭代目标

首版已有可信的规则结算、六席同步、断线恢复与原创故事，适合验证一次短篇。但角色、敌人、技能和场景推进仍与 Python 常量/条件分支紧密耦合；没有创作者编辑、校验、发布、复用内容的闭环。自由生成依赖固定幕数骨架，不能等同无限制自由跑团。

本轮的目标应是“可持续生产和运行冒险的自托管内容平台”：创作者修改数据即可创建另一份可玩冒险；玩家不知道这些数据来自内置、手工或生成，始终使用同一权威规则引擎。

## 2. 先拆开两类模式

| 维度 | 选项 | 用户承诺 |
| --- | --- | --- |
| 内容来源 | 内置剧本 / 手工创作 / LLM 生成草稿 | 决定冒险从哪里来；生成草稿也必须校验与发布 |
| 交互模式 | 预设引导 / 自由叙事 / LLM 引导 | 决定玩家如何表达与获得建议；不改变规则可信度 |

预设引导展示策划好的合法动作。自由叙事允许玩家描述计划、人物对白和探索意图，但不把自然语言当作已结算事实。LLM 引导把意图映射成已注册动作建议，展示检定、消耗、目标等供玩家确认，再执行脚本。不能用三个不同名称表示同一套固定按钮，也不能把“自由创作”误解成“随机换一段开场白”。

创建房间时先选“玩什么”，再选“如何主持”。无模型时禁用需要模型的功能并说明原因；手工创作和预设游玩应不依赖模型 Key。

## 3. 管理系统信息架构

新增“创作工坊”，与玩家冒险桌分开。主导航建议为“我的冒险 / 剧情本 / 技能卡 / 怪兽卡”。保留夜色、黄铜与航海图语言，但工作区以阅读和编辑效率为先。

| 工作区 | 列表 | 编辑表单 | 预览与操作 |
| --- | --- | --- | --- |
| 技能卡 | 名称、类型、状态、版本、被引用数量 | 名称/说明、合法效果、骰式、属性、目标、消耗、使用时机 | 人类可读规则摘要；复制、保存草稿、校验、发布、归档 |
| 怪兽卡 | 名称、生命、护甲、技能数量、状态 | 基本属性、HP/AC、技能引用、行为策略 | 怪兽卡及实际可执行动作；预览依赖错误 |
| 剧情本 | 标题、简介、节点数量、发布状态 | 场景节点、开场节点、行动、成功/失败后续、遭遇、结局 | 节点清单或流程预览；引用检查、试运行、发布 |

编辑器必须提供常规表单，不让普通创作者从空 JSON 开始。JSON 导入/导出用于备份、共享和高级编辑；服务端采用与表单相同的严格 schema，不执行任意 Python/JavaScript/表达式。

列表应支持搜索与类型/状态筛选。空状态给出“创建第一张卡”及可复制的内置示例。删除优先归档；内置示例只读，用户通过复制产生自己的草稿。

## 4. 内容生命周期是必要能力

推荐统一结构：稳定内容 ID、类型、草稿 revision、发布版本、标题、说明、标签、schema_version、更新时间、内容 payload。

1. **创建/复制**：从空白或内置模板获得草稿。
2. **编辑/保存**：检查字段；带 expected_revision 防止另一个标签页静默覆盖。
3. **校验**：返回字段路径、问题原因和修改建议，保留用户输入。
4. **发布**：引用必须存在且可执行，形成不可变发布版本。
5. **使用**：房间创建时锁定剧本及其传递依赖快照；后来编辑或归档不影响进行中的团。
6. **修订**：从发布版本继续编辑并产生下一版，而非覆盖旧版。
7. **归档/导出**：已发布依赖不能被无提示硬删除。导出可移植内容包，导入时整体校验，失败不留下半套内容。

对于技能→怪兽→剧情本的引用关系，发布校验应递归验证依赖。显示“该怪物使用技能 A / B”“该技能被 3 个内容引用”。禁止发布引用不存在的技能、无开场节点、跳转目标缺失、没有任何可达结局的剧情本。允许循环剧情时需避免把合法回访一概拒绝，但应警告无法退出的闭环。

## 5. 关键用户旅程

**创作者**：进入工坊 → 复制内置技能卡并改为另一种伤害 → 创建怪兽并引用该技能 → 新建有调查与战斗分支的剧情本 → 校验错误就地定位 → 发布 → 一键以该版本开房 → 在桌面看到真实怪兽与技能效果。

**玩家**：首页选择已发布剧本 → 看清人数、题材、规则范围、主持模式 → 入席 → 执行动作前看目标/消耗 → 确认后看到骰点凭据与叙事 → 刷新或离线后恢复。

**LLM 引导**：输入“我想骗过守卫混进去” → DM 给出一张“魅力检定 / 目标守卫 / DC / 失败后果”的合法建议 → 玩家确认 → 服务端结算 → DM 描述已确定的结果。模型输出不存在的技能、目标、伤害数字时拒收，保留玩家原话，允许使用手工动作继续。

**发布后修改**：房间 A 使用剧本 1.0 → 创作者发布 1.1 → 房间 A 不变，新房间 B 可使用 1.1。此流程比“编辑成功”更能证明内容管理真正完整。

## 6. 体验细节与权限

- 编辑器顶部明确草稿/已发布状态与未保存更改；离开前避免无声丢稿。
- 保存、发布、试运行三个动作分开；发布前展示校验摘要，不能只给 HTTP 422。
- 技能选项只呈现引擎已支持效果，未来扩展通过注册新效果处理器实现；禁止出现保存成功却无法执行的卡。
- 怪兽的秘密说明与玩家可见描述分开。玩家快照不得带出全部未探索剧情与隐藏结局。
- 管理写操作需要独立管理员授权；房间邀请码或玩家 token 不具有工坊写权限。密钥不写入导出包。
- 角色扮演、规则结果和系统消息分层，规则凭据用可读公式，原始 JSON 放在高级详情。
- 生成过程显示状态、取消/重试入口；请求失败保留编辑草稿。生成不直接发布内容。
- 手机优先保障阅读、选卡与游玩；复杂剧情图可用节点列表替代横向巨幅画布，表单不横向溢出。

## 7. 本轮验收标准

| 验收 | 成功标准 |
| --- | --- |
| 卡片管理闭环 | 技能卡、怪兽卡、剧情本均可创建、修改、复制、校验、发布、归档与导出 |
| 引用正确性 | 不存在/未发布/类型错误引用不能发布；错误精确到字段路径 |
| 游戏接入 | 自定义怪兽与技能在战斗中实际生效，不能只展示说明 |
| 剧情分支 | 一个非内置剧情本包含至少两个分支，并能到达结局 |
| 版本隔离 | 编辑/归档内容后，已开始房间仍能使用原快照继续 |
| 权限 | 未授权写操作、玩家 token 管理写操作均拒绝；公开目录不泄露管理凭证 |
| 模式差异 | 三种交互方式有明确行为差异且规则引擎共用；缺 Key 行为明确 |
| 并发与恢复 | 草稿冲突不会覆盖；网络重试不重复发布或重复规则动作 |
| 可移植性 | 导出包重新导入后可校验和使用；非法包原子拒绝 |
| 回归 | 原有六人、幂等、战斗、恢复测试继续通过 |

## 8. 何时才能称为成熟产品

上述完成后可以称为“具备内容管理与可扩展运行时的产品版本”。尚不能仅凭 CRUD 和自动化测试宣称全面成熟。进一步需要真实浏览器桌面/手机验收、真实 LLM 端点与长对话测试、多人连续跑团反馈、备份恢复演练、账号与权限生命周期、存档迁移兼容、审计与运维指标、长时运行/容量测试。

完整 5e 规则、商业多租户、地图战术、语音、实时多人协作编辑、可视化任意脚本是独立的大范围能力，不应借“超强扩展性”暗示本轮已经完成。扩展性的证据应是新增内容不改核心引擎、增加合法效果只需实现明确接口，以及旧内容/存档有版本兼容策略。
